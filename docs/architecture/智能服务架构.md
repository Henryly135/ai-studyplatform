# 智能服务架构

本文档描述 `ai-service` 的多供应商模型目录、聊天与向量模型配对、多向量索引以及 RAG 调用边界。平台只支持 Gemini、GLM 和 OpenRouter；DeepSeek 不在模型目录、管理入口或运行时适配范围内。

## 设计目标

- 生成与向量调用经过统一服务入口，不在聊天、检索或测验工作流中硬编码供应商。
- 用户只选择聊天模型，后端从受控模型目录派生对应的向量模型。
- 同一个知识块可保存多套 1024 维向量，切换聊天模型时直接切换向量空间，不临时重建资料。
- Provider Key 只由管理员配置并加密存储，不下发给浏览器，也不写入仓库。
- 聊天响应、索引状态和遥测记录都能说明实际使用的聊天模型与向量模型。

## 供应商与模型配对

模型不是通过供应商接口动态发现的。受支持模型及其能力由代码中的受控目录定义，启动时同步到数据库；数据库保存启用状态、默认值、配对关系和管理员凭据状态。

| 聊天供应商 | 聊天模型示例 | 后端派生的向量模型 | 维度 |
| --- | --- | --- | ---: |
| Gemini | Gemini 3.5 Flash-Lite、Gemini 3.6 Flash | Gemini Embedding 2 | 1024 |
| GLM | GLM 4.7 | GLM Embedding-3 | 1024 |
| OpenRouter | OpenRouter Auto、目录内的 OpenRouter 模型 | OpenAI Text Embedding 3 Small via OpenRouter | 1024 |

配对关系属于模型目录数据，而不是前端约定。OpenRouter Auto 的聊天路由由
OpenRouter 决定，其向量仍通过 OpenRouter 凭据和 OpenRouter Embedding API
生成。

## 用户和管理员的选择边界

普通用户在课程聊天中只选择聊天模型。前端展示该模型配对的向量模型和课程索引状态，但不允许单独提交或覆盖 `embeddingModelId`。

管理员负责：

- 为 Gemini、GLM、OpenRouter 保存或删除 Provider Key。
- 执行供应商健康检查。
- 设置平台默认聊天模型组合。
- 查看每个供应商、课程和资料的向量回填状态。

管理员设置默认聊天模型后，后端同步派生默认向量模型。AI 测验、学习画像等后台工作流使用管理员默认聊天模型；需要检索的工作流使用它配对的向量模型。课程聊天可使用用户选择覆盖默认聊天模型，但不会改变后台任务的默认值。

新保存或替换的凭据先进入 `unknown`。普通调用与用户模型目录只把
`health_status=ready` 的供应商视为可用；`unknown`、`failed` 和 `quota` 都会给出
明确的不可用原因。管理员健康检查是唯一允许绕过这道状态门的调用，它仍然要求
凭据已配置且启用，并依次验证真实聊天与配对的 1024 维 Embedding。检查成功后写入
`ready` 并再次触发历史资料回填，避免初次保存凭据时因尚未健康而漏掉该向量空间。

## 聊天模型解析

课程聊天按以下优先级解析聊天模型：

1. 请求显式提交且可用的 `model_id`。
2. 当前用户仍然可用的历史选择。
3. 管理员设置的默认聊天模型。
4. 初始化时配置的默认聊天模型。

模型解析完成后，后端读取目录中的 `pairedEmbeddingModelId`。前端自动选中模型后也必须把解析出的 `modelId` 映射到请求的 `model_id`，因此页面显示、请求参数和实际调用保持一致。

系统工作流不使用普通用户偏好，直接从管理员默认聊天模型派生模型组合。

## 统一模型调用层

生成调用统一进入模型调用服务：

```text
业务工作流
  → 解析聊天模型
  → 读取并解密该 Provider 的凭据
  → 选择生成 Adapter
  → 调用 Provider
  → 标准化输出、错误和遥测
```

Gemini 使用 Gemini Adapter；GLM 和 OpenRouter 使用 OpenAI-compatible Adapter。业务工作流不直接构造 Provider URL，也不读取供应商环境变量。

向量调用统一进入 Embedding 调用服务：

```text
业务工作流
  → 传入 embeddingModelId 和文本用途
  → 从模型目录读取 Provider、模型名、维度和 Adapter 类型
  → 读取并解密 Provider 凭据
  → embedQuery 或 embedDocument
  → 校验数量和 1024 维长度
  → 归一化向量并记录遥测
```

Adapter 分为 Gemini Embedding Adapter 和 OpenAI-compatible Embedding
Adapter。Gemini Embedding 2 使用内容前缀区分检索 query 与 document，并请求
1024 维输出；GLM Embedding-3 与 OpenRouter Embedding 共用后者，但使用各自
的 base URL、模型名和凭据。

旧的 Gemini 专属 LangChain Embedding 路径及 `AI_EMBEDDING_PROVIDER`、`AI_EMBEDDING_MODEL` 运行时开关已经删除。供应商、模型、版本与配对关系只从受控模型目录解析。

## 多向量知识库

资料文本只提取和切分一次。模型无关的知识块与模型相关的向量分开保存：

```text
知识源
  └─ 知识块
      ├─ Gemini Embedding 2 @ 1024
      ├─ GLM Embedding-3 @ 1024
      └─ OpenRouter Text Embedding 3 Small @ 1024
```

向量记录至少包含：

- `chunkId`
- `embeddingModelId`
- `embeddingVersion`
- `embeddingDimension`
- `embedding`
- 索引状态和时间戳

同一知识块、模型和版本只能有一条活动向量。资料内容变化后，相关知识块和全部模型向量一并失效，再由索引任务重建；stale 或 inactive 的知识块不能被回填任务复用。

资料上传或更新后的 Fan-out 流程：

1. AI worker 读取 MinIO 或本地存储中的资料。
2. 提取文本并标准化换行。
3. 生成模型无关的知识块。
4. 找出已经配置、启用且支持 Embedding 的模型。
5. 分别生成并 Upsert 每套向量。
6. 更新每个资料、课程和向量模型的覆盖率与状态。

管理员后续新增 Provider Key 时，系统为已有知识块创建该 Provider 的回填任务，不重复提取和切分资料。

## RAG 调用链

课程聊天以 GLM 为例：

```text
用户选择 GLM 4.7
  → 请求携带 GLM chat model_id
  → 后端派生 GLM Embedding-3
  → 为问题生成 GLM 查询向量
  → 只检索 GLM Embedding-3 当前版本的课程向量
  → 组装课程上下文与来源
  → 使用 GLM 4.7 生成回答
  → 返回实际聊天模型、向量模型和来源
```

检索必须同时过滤课程或模块授权范围、`embeddingModelId` 和 `embeddingVersion`。维度相同不代表向量空间兼容，禁止跨模型混用向量。

检索前统一生成不可变的 readiness 快照，包含实际聊天模型、配对向量模型、`embeddingVersion` 和当前课程/模块的覆盖率。只有精确模型与版本的覆盖状态为 `ready` 才会生成查询向量；`partial`、`not_indexed`、`building`、`failed` 都返回 `AI_RAG_INDEX_NOT_READY`，禁止静默检索部分向量。

只有课程或模块确实没有任何已发布资料时，状态才是 `empty`，课程聊天可明确进入普通聊天模式；存在已发布资料但尚未产生知识块时仍是 `not_indexed`。AI 测验不允许 `empty` 降级，返回 `AI_RAG_NO_MATERIALS`；模型组合不可用时返回 `AI_RAG_PROVIDER_UNAVAILABLE`。

## 主要工作流

### 资料索引

学习服务登记资料并通知 AI 服务创建索引任务。Celery worker 负责读取、提取、分块、多模型向量 Fan-out、状态更新和失败重试。

### 课程聊天

FastAPI 层校验用户、课程与模块权限；模型解析器生成聊天/向量模型组合；检索服务查找对应向量空间；生成服务调用用户选择的聊天模型；会话、来源和实际模型信息被保存用于审计。

### AI 测验

测验检索在工作流开始时解析一次管理员默认模型组合，并把实际聊天模型、向量模型及版本写入检索上下文；规划和出题显式复用该聊天模型 ID，不读取教师或学生的模型偏好，也不会在同一次运行中重新选择默认模型。输出必须经过题目数量、选项、答案与解析校验。

### 学习画像

画像工作流使用管理员默认聊天模型，不使用课程聊天中的个人模型偏好，也不需要 Embedding。

## 失败隔离与安全边界

- RAG 只能检索当前用户有权访问的课程资料。
- 一个 Provider 的索引失败不能破坏其他 Provider 已完成的向量。
- Provider HTTP 状态、结构化错误体、超时和畸形响应统一转换为稳定的内部错误。
- HTTP 200 但响应体包含 `error` 仍按失败处理。
- 凭据接口只返回脱敏状态；日志、响应和遥测不保存完整 Key。
- 模型未配置、健康检查失败或向量覆盖未完成时，不把该模型标记为 RAG 就绪。

## 运维检查

对外演示或发布前至少确认：

- Gemini、GLM、OpenRouter 目录中没有 DeepSeek。
- 三个 Provider 的聊天和 Embedding 健康检查均通过。
- 演示课程在三套向量模型下的覆盖率均为 100%。
- 在同一课程依次切换三个聊天模型时，响应中的聊天模型和向量模型与配对目录一致。
- 切换模型不会触发临时资料重建，也不会检索其他模型的向量。
