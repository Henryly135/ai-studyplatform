# 后端分层边界说明

本文档记录后端服务中的控制器、服务、仓储、模型和 schema 职责边界。代码路径、类名和数据库字段名保持原样。

## 推荐调用方向

```text
controller -> service -> repository -> model
```

不要让底层反向依赖上层，也不要让控制器直接写复杂业务规则。

## 目录映射

以 `services/identity-service/app/` 为例：

- `api/`：控制器层，负责 HTTP 请求、依赖注入、状态码和响应模型。
- `services/`：业务服务层，负责业务规则、权限判断、跨仓储编排和事务含义。
- `repositories/`：仓储层，负责数据库查询和持久化。
- `models/`：模型层，负责 SQLAlchemy 表映射和关系。
- `schemas/`：schema 层，负责请求和响应数据结构。
- `db/`：数据库会话和连接配置。
- `core/`：密码、JWT、配置、邮件和通用安全能力。

## 控制器层

控制器应该只做这些事：

- 声明路由。
- 读取请求参数。
- 注入数据库会话和当前用户。
- 调用业务服务。
- 把业务结果转换成响应。

控制器不应该：

- 直接写 SQL 或 ORM 查询。
- 直接实现复杂业务规则。
- 绕过服务层操作多个仓储。
- 记录敏感信息，例如密码、token、验证码或真实 API key。

## 服务层

服务层负责业务规则，例如：

- 登录、注册、邮箱验证和密码重置。
- 教师审批和邀请。
- 课程发布、模块发布、资料上传和测验发布。
- 课程报名、学习进度和权限校验。
- RAG 检索、AI 调用和学习画像更新。

服务层可以编排多个仓储，但应保持事务边界清晰。跨服务调用应通过内部 API 或消息任务完成，不直接访问其他服务数据库。

## 仓储层

仓储层只负责数据访问：

- 根据主键、UUID、状态和筛选条件查询数据。
- 新增、更新、删除数据库记录。
- 封装分页和排序查询。
- 返回模型对象或简单数据结构。

仓储层不应该判断用户角色，也不应该决定某个业务操作是否允许执行。

## 模型层

模型层只描述数据库结构：

- 表名。
- 字段类型。
- 索引。
- 外键关系。
- ORM relationship。

模型层不放业务流程，也不调用服务或仓储。

## Schema 层

Schema 层负责请求和响应的结构约束。公开 API 优先使用 camelCase 字段；内部数据库和 Python 代码可以继续使用 snake_case，但需要在边界处明确转换。

## 事务边界

- 一个 HTTP 请求通常使用一个数据库会话。
- 服务层决定何时提交或回滚。
- 仓储层不主动提交事务，除非该服务已有明确约定。
- 异步任务失败时必须记录失败状态，不能让任务静默丢失。

## 新代码规则

- 新接口先确认所属服务边界。
- 新业务逻辑放入 service，不塞进 route。
- 新查询放入 repository，不散落在控制器。
- 新响应结构放入 schema，不直接返回随意字典。
- 新跨服务能力优先使用内部 API 或任务，不共享数据库连接。
