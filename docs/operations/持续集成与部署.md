# CI/CD 说明

本文档记录持续集成、部署前检查和 AI 多供应商发布门槛。工作流文件位于 `.github/workflows/`，部署通过 `workflow_dispatch` 手动触发。

## CI 触发

CI 在以下情况运行：

- 推送到 `feature/**`、`refactor/**`、`fix/**`、`develop` 或 `main`。
- 创建或更新目标为 `develop` 或 `main` 的 pull request。

合并前应保证与变更相关的所有任务通过。

## CI 检查内容

### 共享包

```bash
pytest packages/platform_common/tests -q
```

### 前端

```bash
cd frontend
npm ci
npm run lint
npm test
npm run build
npm run audit:ci
```

`audit:ci` 默认阻断全部 high/critical 漏洞。目前仅对 React Router
`GHSA-qwww-vcr4-c8h2` 设置了截至 2026-09-30 的精确临时豁免：公告只影响实验性
RSC Action，本项目是浏览器 SPA，未启用 RSC。豁免按公告编号、URL、包名和严重级别
共同匹配；出现任何其他 high/critical、公告内容变化或到期未复核时，CI 仍会失败。

### 后端服务

CI 为四个后端服务安装各自依赖和 `platform_common`，执行导入检查与完整测试目录：

```bash
cd services/identity-service && pytest tests -q
cd services/communication-service && pytest tests -q
cd services/learning-service && pytest tests -q
cd services/ai-service && pytest tests -q
```

`learning-service` 不能只做导入检查，`ai-service` 也不能只执行画像和测验目录。Provider Adapter、模型目录、管理员模型 API、多向量索引和检索测试都必须属于完整 `tests` 套件并进入 CI。

标准 PR CI 使用 Mock HTTP Server 或伪造传输层验证 Provider contract，不读取真实 Gemini、GLM 或 OpenRouter Key，不产生付费调用。真实 Provider 冒烟测试只允许在受保护环境中手动执行。

### Docker 与基础设施

Compose 使用独立任务做静默解析：

```bash
docker compose --env-file .env -f infra/docker-compose.yml config --quiet
```

CI 还会：

- 构建 Docker 镜像。
- 启动完整服务栈并验证 nginx 到各服务的路由。
- 检查 Redis、Celery worker、MinIO 私有 bucket 和初始化任务。
- 验证生产配置对占位密钥、弱 JWT 密钥和非 HTTPS 前端地址执行 fail-fast。
- 在失败时输出受限长度的容器状态和日志。

## AI 相关 CI 环境

- 测试向量维度固定为 1024。
- 模型目录只允许 Gemini、GLM、OpenRouter。
- CI 不把任何真实 Provider API Key 作为成功条件。
- Provider Key 加密、脱敏、覆盖和删除必须用测试密钥验证。
- 日志和测试快照不得包含完整 Key。
- HTTP 200 但响应体包含 `error` 必须作为 Provider 调用失败。

## 部署前门槛

触发部署前确认：

- 目标提交已经通过完整 CI。
- 数据库迁移与应用版本匹配。
- `AI_PROVIDER_KEY_ENCRYPTION_SECRET` 是稳定、强随机且已备份的部署 Secret。
- 管理员已经为计划使用的 Gemini、GLM、OpenRouter Provider 保存 Key。
- 默认聊天模型存在且其配对向量模型可用。
- 现有资料在该向量模型下已完成回填。
- Demo 环境按 [`Demo演示指南.md`](Demo演示指南.md) 完成三 Provider 预检。

Provider Key 存在平台加密凭据表中，不应写入 GitHub Workflow、部署脚本或仓库 `.env`。用于解密这些凭据的 `AI_PROVIDER_KEY_ENCRYPTION_SECRET` 必须由部署环境提供；更换它之前必须制定凭据重新加密方案。

## 必要部署 Secret

至少包括：

- SSH 连接信息。
- 数据库密码。
- JWT 密钥。
- 内部服务密钥。
- `AI_PROVIDER_KEY_ENCRYPTION_SECRET`。
- SMTP 配置。
- MinIO 访问密钥。

真实值不得写入仓库、示例文件、构建日志或测试夹具。

## 发布顺序

1. 备份数据库，并确认原始课程资料仍可读取。
2. 应用新增式数据库迁移。
3. 部署兼容新旧向量结构的应用版本。
4. 运行 Gemini、GLM、OpenRouter 向量回填。
5. 检查每套向量覆盖率和错误记录。
6. 将检索切换到多向量表。
7. 完成课程聊天和 AI 测验冒烟测试。
8. 稳定一个版本后再删除旧向量列或旧配置。

## 回滚

- 在切换检索前失败：停止回填任务，回滚应用；新增表可以保留。
- 切换检索后失败：恢复上一版本应用并重新启用旧检索路径，保留新向量以便排查。
- 不通过删除原始资料来回滚索引。
- 已删除的 Provider Key 无法从脱敏信息恢复，需要管理员重新录入。

部署失败时保留容器日志、迁移版本、索引覆盖率和失败 Provider 的脱敏错误码，禁止记录完整请求或凭据。
